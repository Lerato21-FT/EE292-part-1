# Referee report: FMR visualizer (branch `review/2026-11-16-referee`)

I used only Read, Grep and Glob. I ran nothing, wrote nothing and made no network calls.

## Verdict

The core physics is correct. μB/h = 13.99624555 GHz/T (`pipeline.py:16`) matches CODATA to within 1e-7. Oe→T uses ×1e-4. The derivative-Lorentzian has extrema at ±Γ/√3, so ΔHpp = 2Γ/√3 (`pipeline.py:154`) is right, and so is the inverse seed Γ = ΔHpp·√3/2 (`:124`). The damping conversion α = slope·√3·(gμB/h)/2 (`:297-299`) is algebraically the same as ΔHpp = ΔH0 + 4πα f/(√3γ) with γ = 2π·gμB/h. Both Kittel forms match `docs/fmr-model.md` and the README. At φ=0 the in-plane form (B+B4)(B+B4+Beff) agrees with the common (B+B4cos4φ)(B+Meff+B4(3+cos4φ)/4) convention.

The AGENTS.md invariants hold:
- **Frontend computes nothing.** `app.js` only formats numbers with `toFixed`/`toPrecision` and re-checks input ranges.
- **Localhost only.** The port is published as `127.0.0.1:${FMR_PORT}:8000` (`compose.yaml:9`).
- **No runtime installs.**
- **No secrets** in the repo.

The real weaknesses are elsewhere:
- The smoke gate cannot fail on a failed fit.
- `make clean` does not do what ARCHITECTURE claims.
- In-plane data with signed fields hits a scipy error that the user cannot interpret.
- Several validation tests cannot fail if the check they are named after is removed.
