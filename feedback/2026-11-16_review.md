# Review of the FMR visualizer: 2026-11-16

Reviewer: Claude (Claude Code session), plus an independent read-only
referee agent (`.claude/agents/referee.md`). The referee's full report is in
`notes/2026-11-16.md`. Reviewed revision: `main` at `8527d4a`.

## Verdict

The engineering is better than most course projects at this stage. The
containers are locked down, the app listens on 127.0.0.1 only, uploads are
validated, the backend/frontend split is clean, and there's a real
`make verify` gate with browser checks. The physics core is correct as far
as I can check by hand.

The weaknesses are scientific credibility and process, not code.

- **The tests can't catch the errors a physicist cares about most.** They
  build their expected values from the same constant and the same formula
  the code uses.
- **The app reports fitted numbers with no uncertainties and no quality
  gate.**
- **Feedback from two peer reviews a month ago is still mostly unaddressed.**

Right now I would not trust a number from this app in a paper without
redoing the fit by hand.

## What I checked and found correct

- μB/h = 13.99624555 GHz/T (`src/app/pipeline.py:16`). This matches CODATA.
- The derivative-Lorentzian peak-to-peak width ΔHpp = 2Γ/√3, and its
  inverse for the initial guess (`pipeline.py:124`, `:154`).
- Damping: α = slope·√3·(γ/2π)/2, which follows from
  ΔHpp = ΔH0 + 4πα f/(√3γ) (`pipeline.py:297-299`).
- The perpendicular Kittel relation f = (gμB/h)(B − Beff,⊥)
  (`pipeline.py:220-222`).
- The frontend only formats numbers the backend returns (`toFixed` and
  `toPrecision` in `src/web/app.js`). The "backend computes everything"
  invariant holds.

## Criticism

### Major

1. **The tests that should guard the physics are circular.**
   `tests/test_pipeline.py:11` imports `BOHR_MAGNETON_OVER_PLANCK_GHZ_PER_T`
   from the code under test. The Kittel test (`:55-62`) and the damping test
   (`:75-76`) build their expected data with that constant and the same
   equations the code uses.
   - If someone changed the constant to 28.0 (the electron's γ/2π in GHz/T,
     a classic mix-up), the unit tests would still pass.
   - If the √3/2 factor were wrong in the damping code and someone "fixed"
     the test to match, nothing would notice.
   - The only independent anchor is the broadband regression test (`:109-115`).
     Its tolerances are about ±1 % on g and **±20 % on α** (0.00492 ± 0.001),
     and its expected values are the app's own earlier output, not an
     independent result.

   *Fix:* hard-code the constant in the test from CODATA. Add at least one
   test whose expected g and α come from outside this code: a hand
   calculation, a published dataset, or an fit done independently in another
   tool. Tighten the α tolerance or justify it.

2. **No parameter uncertainties.** `curve_fit` returns a covariance, and
   every call throws it away (`pipeline.py:130`, `:197`, `:253`).
   `np.polyfit` is called without `cov=True` (`:292`). The UI shows g to 4
   decimals and B4 to 5, which implies a precision nobody has established.
   For the four-fold term, which luyunqi and your own notes already call
   unreliable from a single azimuth, a ± would show whether B4 = −0.020 T
   differs from zero at all.

   *Fix:* return 1σ uncertainties from `pcov` and show "value ± σ".
   Round the displayed digits to the uncertainty.

3. **A noisy linewidth slope throws away a good Kittel fit.**
   `fit_linewidth` raises an error when slope < 0 (`pipeline.py:294`). That
   happens inside the same `try` as the Kittel fit (`:503-511`), so the
   result is that *neither* fit is reported. For low-damping films (your own
   synthetic case uses α = 0.0002), noise alone can make the slope slightly
   negative. Then g and Beff,⊥, which are perfectly well determined,
   disappear.

   *Fix:* report the two fits independently, and flag α as
   "not resolved / consistent with zero" instead of failing.

4. **No fit-quality gate.** This was suggested by luyunqi on 2026-10-13
   (flag R² < 0.98) and noted again in `notes/2026-10-21.md`. Nothing has
   changed: a terrible resonance fit flows straight into the Kittel and
   damping fits. The exclusion feature helps, but it relies on the user
   spotting bad traces by eye.

   *Fix:* flag, and optionally auto-exclude, sweeps below a threshold you
   justify in `PROMPT.md`. Show the flag in the UI.

5. **Modulation broadening is not considered.** The filenames say
   `2.0OeRMS` modulation, which is about 5.7 Oe peak-to-peak. The
   perpendicular workflow assumes linewidths around 10 Oe. When the
   modulation is a sizable fraction of ΔHpp, the measured derivative line
   broadens and distorts. That biases ΔH0 and can bias α.

   *Fix:* at minimum, document the condition (modulation ≲ ΔHpp/3) in
   `docs/fmr-model.md` and warn when it is violated. Better still, read the
   modulation amplitude from the filename and report it.

6. **A course API key is still in git history.** `ee292m.env` was
   committed in `3fee3a2` and deleted from the tree on 2026-10-15, but anyone
   who clones the repo can recover it.

   *Fix:* rotate the key. Deleting the file was not enough.

### Process

7. **Peer feedback has sat for a month.** From allenduh (2026-10-14): an
   intro for non-specialists, typeset equations, a nicer linewidth PNG, and
   a "so what". From luyunqi (2026-10-13): CSV export, a quantitative
   `PROMPT.md`, and the motivation, milestones and top three risks in the
   README. Today, `README.md` has no "why it matters", milestones or risks
   section, and `PROMPT.md` has no tolerances or thresholds. CSV export is
   only now reappearing, in `notes/2026-11-11.md`. Of the eight suggestions,
   about one has been addressed. That's the clearest signal in this review:
   you collect feedback but don't close the loop. None of it is in
   `TASKS.md`.
8. **You keep making exceptions to your own git rules.** AGENTS.md says
   `main` changes only through PRs. `f47cc3b` went straight to `main`, and
   today you approved two more direct pushes, "this one time" twice. Each
   one is defensible, but the rule is becoming a suggestion. Either keep
   it or rewrite it to say what you actually do (for example, "docs-only
   changes may go straight to `main`").
9. **Git identity isn't configured on this machine.** The history mixes
   at least five hostname-derived `@…SUNet` author addresses (one for each
   machine or network session) with a Gmail and a GitHub noreply address. Set `user.name` and `user.email` in this repo yourself so the
   history is attributable.
10. **Work is bursty.** Commits landed on 10 of the 47 days before today, with long gaps
    (Oct 27–Nov 2 and Nov 4–10 had nothing). That's fine for a course, but
    the daily-notes habit from Oct 19–21 stopped. Notes are the cheapest way
    to keep `TASKS.md` and the feedback loop alive.

### Minor

11. `README.md:236` has a stray `# EE292-part-1` heading left over from the
    GitHub-generated README.
12. `load_measurement` re-lists the whole directory for every file
    (`pipeline.py:332`), so loading N files costs O(N²) directory listings.
    It's harmless at 49 files, but it's the first thing to fix if anyone
    uploads 1000.
13. The upload byte limit (`dataset_store.py:118`) is checked only after
    Starlette has already received the whole request body, and `/tmp` is a
    tmpfs. A very large request uses RAM before it's rejected. It's
    acceptable for a localhost-only tool; just say so in ARCHITECTURE.md.
14. The out-of-plane default linewidth of 10 Oe is duplicated in
    `api.py:97-98` and `pipeline.py:381-382`. Keep one source of truth.
15. In-plane Beff,⊥ is bounded to ≥ 1e-5 T (`pipeline.py:202`). That's fine
    for this sample, but it silently can't represent a film whose
    perpendicular anisotropy exceeds its demagnetization. Document that
    limit.

### From the referee, checked by me

The referee found these, and I missed them. I checked each against the files
(severity is mine):

- **R1 (major). `make verify` has a smoke check that can't fail on a failed
  fit.** `Makefile:65` runs `grep -q '"kittel_fit"'`, but that key is
  *always* in the response (`pipeline.py:486` sets it to `None`). A broken
  fit still prints "API smoke check passed: Kittel fit returned." Your gate
  is weaker than ARCHITECTURE.md:153 claims. *Fix:* match
  `'"g_factor":[0-9]'` or `'"fit_error":null'`.
- **R2 (major). `make clean` doesn't return to a fresh clone.**
  `Makefile:78-80` leaves `.cache/` (buildx metadata and kept
  `fresh-verify.*` clones) and `artifacts/` in place. With `--rmi local`, the
  named images (`fmr_visualizer:latest`, and the browser image, whose profile
  isn't activated) are very likely kept too. ARCHITECTURE.md:143 says
  otherwise. I confirmed this by reading the Makefile, not by running it.
- **R3 (major, unconfirmed). In-plane data with a resonance at ≤ 0 Oe**
  probably fails with scipy's raw "`x0` is infeasible" message
  (`pipeline.py:193-201`: the lower bound for B4 becomes positive while
  `p0` stays at 0). The signed-field work from 2026-10-26 was tested only
  out-of-plane. *Needs one test to confirm.*
- **R4 (minor). Several validation tests can't fail.** For example,
  `tests/test_api.py:51` would still get 422 if the ID length and count
  limits were deleted. The upload-safety branches (size, count, duplicate
  and `../` names) in `dataset_store.py:96-125` have no tests at all.
- **R5 (minor). `/docs` (Swagger) loads from a CDN**, which contradicts
  "no browser CDN" in ARCHITECTURE.md:13 and won't render offline.
- **R6 (nit). `.DS_Store` is tracked in git** and isn't in `.gitignore`.

I agree with the rest of its list (uncertainties, the bound on in-plane
Beff, the duplicated 10 Oe default, O(N²) loading) and have merged those
into items 2, 12, 14 and 15 above. It also flagged error messages that
expose container paths (`pipeline.py:322,325`). That's a nit for a
localhost tool.

**The main risk is my own session.** It has all three legs: private data,
untrusted content, and several ways out. Nothing but instructions limits
what I can write or send, so a prompt injection hidden in an uploaded CSV
or a peer-review file could in principle make me push or email something.

To cut it down:
- Turn on Claude Code's sandbox, or run agent sessions in a dev container
  with only this repo mounted.
- Add a project `.claude/settings.json` that denies `git push` without
  asking.
- Detach connectors you don't need for this project, especially Gmail.
- Use the referee as a real custom agent (restart Claude Code once so it
  loads), not the general-purpose fallback, so its read-only limit is
  enforced rather than requested.
