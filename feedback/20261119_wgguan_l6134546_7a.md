### 2. The README has a drawing of the capstone as a system, and from it I can say where each part runs and how code and data reach it.

Verified: yes

The machines or containers, and how code and data arrive:

The README has no drawing of the system. It has the run commands and the equations, and ARCHITECTURE.md has a folder tree, so I put the picture together from docker/compose.yaml and the Dockerfile. Everything runs on one laptop in Docker. The app container runs uvicorn on port 8000, published only on 127.0.0.1 port 8765, as the host user, with a read only filesystem except a /tmp tmpfs. A second container, only for make browser, runs Chromium against its own copy of the API and writes screenshots to the artifacts folder, its only mount. Code and the 49 demo CSVs arrive by being copied into the image at build time (src to /work, broadband_100 to /data), not mounted, because reading the macOS bind mount failed. Uploaded folders arrive over HTTP and live only in the container's /tmp until it stops. Dependencies come from the two lock files at build time.

### 4. We have discussed each boundary in the system (between front end and backend, data and database, or services) and whether it is real.

Verified: yes

The boundaries, and which one is not real yet:

There are three boundaries and no database. Browser to backend is HTTP with JSON, typed by the Pydantic models in models.py and published at /docs, and the page computes no results, so that one is real. API to science is real too, since api.py holds routes only and calls one function per endpoint in pipeline.py. Upload to active data goes through DatasetStore, which validates the whole folder in /tmp before swapping it in under a lock, and that one is real. The one that is not real yet is the model knowledge across the browser boundary. app.js repeats the allowed starting field range (app.js line 154, also pipeline.py line 497 and inside both fit functions) and types the Kittel equation again for the plot label (app.js line 198), so a change to a model has to be made on both sides.
